# rx — remote process execution over SSH (agent transport)

This guide ships with rx {{VERSION}} and describes that binary. `rx --version`
tells you what is installed; check it before reporting behaviour.

Read this whole file once; it is short and complete. It describes capabilities,
not a mandatory workflow — compose the commands as the task needs.

rx is one tool in your box, not a replacement for it — use whatever fits the
task. Prefer rx when you want its edges: verbatim argv/stdin (nothing to quote),
structured exit/signal/error results, or detach-and-reattach. For running a
command and needing its exit code or clean output, rx beats ad-hoc `ssh host
'…'`. rx has no secret store of its own and no dependency on one: `put -` takes
whatever a pipeline hands it — `pass`, `op read`, `sops -d`, or rxv
(`rxv skill`), a separate tool built to this same contract, so its output and
errors read the way rx's do.

## Start here

  rx ping HOST          # reachable? which rxd? which OS/distro?
  rx deploy HOST        # only if ping answered not_deployed
  rx run HOST -- CMD    # then work

First contact with an unprepared host **fails on purpose**: rx does not install
anything on a machine you merely pointed it at. `not_deployed` is that refusal,
and its `hint` names the one command that fixes it. Deploy is a single static
binary and needs nothing on the remote — no runtime, no package, no daemon to
manage. Expect the sequence above once per host, then never again.

## Which command

Most work is `run` plus `put`/`get`. The process verbs (status, stdout, stderr,
list, clean, write, close-stdin, kill, wait) are for processes you keep.

  one command, want its output and exit code  →  run
  long-lived, streaming, or interactive       →  start, then stdout / wait
  raw bytes in and out, no JSON in the way    →  start --pipe
  move a file, either direction               →  put / get

Commands run detached on the remote under a private per-user state dir; stdout
and stderr are captured to files that survive disconnect. Two ways to start work
over that substrate, and one to block on what you started:
- run   — synchronous. Blocks up to a timeout (--timeout, default 30s); if the
          command outlives it, the process keeps running and a `running` handle
          is returned instead.
- start — returns a handle immediately. For long-lived, streaming, or
          interactive processes you read/write later.
- wait  — block on an already-started process until it exits or a timeout
          (--timeout, default 30s), returning the same completed/running shapes
          as run (no polling).

## Invariants

- Every command that DOES something prints exactly one JSON object on stdout
  (type field), errors included. The exception is `start --pipe`, whose product
  is bytes (data on stdout, JSON handle on stderr).
- Discovery is not an operation and prints plain text, no object: `--help`, `-h`,
  `help`, `--version`, `skill` (this guide), and a bare `rx` with no subcommand.
  None of them has side effects.
- Exit 0 = success · 1 = the call was understood and failed · 2 = the call was
  malformed. On exit 2 stdout stays EMPTY and the typed object goes to stderr —
  a mistyped flag and a rejected argument value are one class of failure, and
  stdout is kept clean because the subcommand is not yet known when the parser
  rejects a call. The one exit-2 case with NO object is a bare `rx`: it named no
  operation, so it prints help to stderr like the rest of discovery.
  `run`/`wait` also propagate the remote command's status:
  `rx run HOST -- false` → exit 1, killed by signal N → 128+N, and a command
  that never started (see exec_error) → 127, so
  `rx run HOST -- missing-tool && next` does not run `next`. The JSON is the
  source of truth.
- A transport failure (unreachable host, auth) still prints a JSON `error` with a
  `code` on stdout and exits 1. The command never ran, and the object is how you
  learn that — not a bare line on stderr. Always read stdout JSON.
- Command arguments and stdin bytes are transported verbatim over the SSH
  channel — no remote shell parses them. There is nothing to escape/quote.
- Process IDs are 8 lowercase hex characters.
- Trust model: rxd runs as the SSH user and is a transport, not a sandbox or
  privilege boundary. It can do anything that user can (write any path via put,
  elevate via `doas` in a command). Your SSH access is the whole trust boundary.
- **stdin is captured whenever it is not a terminal.** `run` reads it and feeds
  it to the remote process; `start` pipes it. That is what makes `cat f | rx run
  HOST -- sort` work — but an agent harness has no terminal, so if your stdin is
  an open pipe nobody ever writes to or closes, these commands wait for EOF and
  appear to hang. Redirect `</dev/null` whenever you do not mean to send input.
  (Arguments are validated first, so a malformed call fails immediately instead
  of blocking, and never swallows a pipeline's payload.)
- JSON follows the destination: pretty on a terminal, compact otherwise. Force
  it with --compact / --pretty, or RX_JSON=compact|pretty.
- Idempotence: asking for a state that already holds succeeds with
  `"changed": false` (`rx daemon start` on a running daemon; `rx deploy` on a
  host already running this exact rxd, which answers `status:"current"` and
  uploads nothing).

## Commands

Listed in the order `rx --help` shows them: the guide, first contact, execute,
observe, control, move files, local machinery.

  skill
  ping  HOST
  deploy HOST... [--binary PATH] [--offline] [--allow-downgrade]
  run   HOST [--cwd DIR] [--env K=V]... [--timeout SECS] [--keep-stdin-open] [--keep] -- CMD...
  start HOST [--cwd DIR] [--env K=V]... [--pipe] [--no-close-stdin] -- CMD...
  wait  HOST ID [--timeout SECS]
  status HOST ID
  stdout HOST ID [--offset N] [--limit N]
  stderr HOST ID [--offset N] [--limit N]
  list HOST
  clean HOST
  write HOST ID [TEXT] [--raw]
  close-stdin HOST ID
  kill HOST ID
  put   LOCAL|- HOST:PATH [--mode OCTAL] [--owner USER] [--group GRP] [--allow-empty]
  get   HOST:PATH LOCAL [--mode OCTAL]
  cache fetch [--version V] [--arch ARCH]... [--force]
  daemon start|stop|status

Global: --compact, --pretty, --auto-deploy off|local|on

Notes:
- Everything after `--` is the remote argv. `--` is optional but disambiguates a
  command whose own flags could collide with rx options; put rx options before
  it. execvp runs the argv directly — no shell, so no globbing/redirection/`;`.
- --cwd and --env set the working directory and environment directly, so you
  don't need a `sh -c 'cd DIR && K=V ...'` wrapper. --env is repeatable and its
  overrides layer on the inherited environment.
- put/get move whole files with constant memory (streamed, no size cap) and are
  safe on flaky links: the receiver installs the file (atomic temp→rename) only
  if the whole transfer arrived — a dropped connection yields
  `incomplete_transfer`, never a truncated file. With a local file the sender
  declares the byte count; with `-` it frames the stream and marks its end, so
  the guarantee holds for input whose length is unknown in advance.
  put writes to the remote (--mode always works; --owner/--group need a
  privileged rxd); get writes to the local path and applies the source's mode
  unless --mode overrides. Both transport bytes faithfully but do NOT snapshot a
  live database — dump/checkpoint first (e.g. `sqlite3 .backup`, `pg_dump`).
- get copies a live file and cannot freeze it: the byte count is fixed in the
  header before the body starts. If the file changes while it is being read, get
  fails with `file_changed` (retryable) and writes NOTHING locally — it never
  silently returns a torn or truncated copy. Expect this on logs and databases;
  snapshot them remotely first, then get the snapshot.
- `put -` streams stdin, so a value can go from a pipeline straight to a remote
  file without ever being written to a local temp file or passed as an argument:

      producer | rx put - HOST:/run/secrets/db_pass --mode 0600

  Mode is applied before the file is visible, so there is no window where it sits
  world-readable — unlike `rx run HOST -- tee PATH`, which creates it at the
  remote umask. With no --mode a put lands 0600, and the `copied` response
  reports the mode the file actually got (octal string, e.g. "0600").
- An empty stdin stream is REFUSED (`empty_stream`, not retryable) rather than
  installed, because `producer | rx put -` where the producer failed sends a
  well-formed stream of zero bytes — installing it would blank an existing file
  and report success. Use `set -o pipefail` to catch the producer's exit status,
  or --allow-empty when an empty file is what you mean.
  pipefail is a REPORTING requirement, not a safety one: the `empty_stream`
  refusal already stops a failed producer from blanking the remote file with or
  without it. What pipefail buys is that the shell — and therefore you — sees
  the failure instead of reading the pipeline as successful.
  Scope: put guarantees "exactly what rx read landed, or nothing landed". It
  cannot tell a producer that finished from one that died mid-output — a pipe
  carries no exit status. Where that matters, write a file first and put that.
- `put -` cannot be retried (stdin does not rewind). Under --auto-deploy=local|on
  it settles that before reading a byte: it probes the host and deploys first.
  Under the default (off) there is no probe — the transfer runs once and a
  mismatched host answers `not_deployed` afterwards. Nothing is installed
  remotely either way, but the producer HAS been read by then, so re-run the
  whole pipeline after deploying rather than expecting rx to resume it.
- `cp` still works as an alias for `put`; prefer `put`, which pairs with `get`.
- get vs `run -- cat`: use `run cat` to read small contents inline; use get to
  materialize a large or binary remote file as a real local path efficiently.
- run: stdin, if piped, is fed to the process, then EOF is sent so readers
  terminate. With no piped stdin, EOF is sent immediately. --keep-stdin-open
  suppresses the EOF. Inline stdin is capped at 4 MiB; larger uses start+pipe.
- run is ephemeral by default: a `completed` response whose output is small
  enough to be seen in full (<=16 KiB/stream) also deletes the remote process dir
  (no leftover state). The dir is KEPT when output is truncated or larger than
  that, or when backgrounded (`running`) — so bigger output stays re-pageable via
  stdout/stderr --offset instead of forcing a re-run. Pass --keep to always
  retain the dir after a completed run.
- stdout/stderr read from --offset and return at most --limit bytes (default
  1 MiB), so draining a large stream is a loop over --offset, not one call.
- write TEXT appends a newline unless --raw. With TEXT omitted and stdin piped,
  the stream is forwarded raw and unbounded (binary-safe). close-stdin sends EOF.
- start --pipe: local stdin → remote stdin and remote stdout → local stdout as
  raw bytes; the JSON handle is written to stderr.
- The local daemon (daemon start|stop|status) is an optional accelerator that
  caches repeated reads of long-running processes locally. It is used only when
  you opt in with RX_DAEMON=1; direct SSH is the default and canonical
  path, and it does not handle ping/deploy/put/get. A daemon that merely happens
  to be running never changes how a command is transported.

## Text encoding

stdout/stderr/data fields pair with an `encoding`:
- utf8   — the JSON string is the literal output; use it directly.
- base64 — output was not clean UTF-8 (binary or embedded NUL); base64-decode it.

## Response shapes (by type)

  completed {id, exit_code|null, signal|null, exec_error?, duration_ms,
             stdout, stdout_encoding, stderr, stderr_encoding,
             stdout_size, stderr_size, stdout_truncated, stderr_truncated}
  running   {id, reason, stdout_size, stderr_size, hint}
  started   {id}
  status    {id, state, cmd, started, ended|null,
             exit_code|null, signal|null, stdout_size, stderr_size}
  output    {data, encoding, offset, size}
  written   {bytes}          # from close-stdin, bytes:0 means EOF sent
  copied    {path, bytes, mode?}     # put result (remote file written)
  got       {path, bytes, mode?}     # get result (local file written)
                                     # mode is octal as a string: "0600"
  killed    {id}
  list      {processes:[{id, state, cmd}]}
  cleaned   {removed:[id...]}
  deployed  {host, arch, version, status, changed}   # one host
            {hosts:[...]}                            # several hosts (see below)
  cache     {action, version, binaries:[{arch, path, sha256, status}]}
  ping      {version, protocol, arch, os, kernel, hostname,
             distro_id?, distro_version?,
             local_version, up_to_date, hint?}
  daemon    {action, running, changed, pid?, detail?}   # daemon start|stop|status
  error     {message, code, retryable, hint?}   # code and retryable are always
                                                # present; see Error codes below

- run and wait yield completed or running. exit_code is null when signal is set.
- deployed: one host is a flat object. Several become `hosts:[…]`, where an entry
  that succeeded carries that same {host, arch, version, status, changed} and one
  that failed carries {host, status:"failed", code, message, retryable, hint?}.
- exec_error is present only when the command never started (the binary wasn't
  found or wasn't executable) — then exit_code and signal are both null and
  stderr carries a `rx: exec …` line. Values: command_not_found · permission_denied
  · exec_format_error · errno_<n>. Branch on this to tell "the tool isn't there"
  (install it, or use another) from "the tool ran and exited 127" — the JSON
  distinguishes them even though rx exits 127 in both cases.
- After an ephemeral completed run the process id is still in the response for
  logging, but status/stdout/stderr for that id return process_not_found.
- state: running | exited(N) | signaled(N) | exited(killed) | exited(unknown) |
  exec_failed(reason)  (reason as in exec_error above; the status view of a
  command that failed to start).
- completed inlines up to the last 256 KiB per stream; when *_truncated is true
  the full output remains readable via stdout/stderr with --offset.
- output.size is the total file size — pass it back as the next --offset to read
  incrementally; size == offset with an exited state means fully drained.

## Error codes (error.code)

  bad_request · invalid_process_id · process_not_found · process_exited ·
  timeout · not_deployed · unsupported · ssh_unreachable · ssh_auth ·
  not_found · incomplete_transfer · empty_stream · bad_host · file_changed ·
  deploy_failed · internal

Branch on code, not message text. `code` is ALWAYS present — when nothing more
specific fits, it is `internal`, never absent — so a switch on it never falls
through to undefined. `retryable:true` means the same call may succeed on retry
(e.g. after an auto-deploy, or a transient ssh_unreachable).

Anything you have to fix yourself is NOT retryable, so a retry loop terminates:
a missing target directory or a path the SSH user cannot write answers
`not_found` / `bad_request` with a hint (not `internal`), and a malformed process
ID answers `invalid_process_id` locally, without contacting the host at all — so
a typo cannot come back as a retryable `ssh_unreachable` from a host that happens
to be down.

## HOST argument

HOST is an ssh destination: `host`, `user@host`, an ssh_config alias, or an
`ssh://` URI. rx rejects anything that is not one — empty, starting with `-`, or
carrying whitespace or control characters — with `bad_host` before it spawns
anything. A destination starting with `-` is the one that matters: ssh would
read it as an option, and `-oProxyCommand=...` runs an arbitrary command on the
CONTROLLER, which is the machine holding your SSH keys and any unlocked vault.
rx also passes `--` ahead of every destination, so this holds even for a code
path that skips the check.

Practical consequence when a host comes from data you did not write (an
inventory file, a ticket, a model's output): pass it through as one argument and
let rx reject it. Do not paste it into a shell string, and do not strip a
leading `-` to "fix" it.

## Deploy and connections

rxd is the remote binary; `rx deploy HOST...` installs the arch-matched build to
~/.local/bin/rxd, downloading it if the local cache lacks it (`--offline` to
refuse, `--binary PATH` to push a local build, and several hosts in one call).
rx multiplexes SSH connections, so repeated operations to a host reuse one
connection.

rx and rxd are two halves of one wire protocol, so the only correct rxd for a
given rx is its own version — there is nothing separate to pin, and upgrading rx
is what moves the pair. What --auto-deploy controls is when *hosts* change:

  off    (default) never deploy as a side effect; a mismatch is a typed
         not_deployed error naming the command that fixes it
  local  may deploy during another command, but only from the local cache
  on     may fetch and deploy during another command

`rx deploy` is explicit and always allowed regardless of this setting. Env
equivalent: RX_AUTO_DEPLOY=off|local|on (1/true still mean on; the older
REM_EXEC_* names still work). rx never
downgrades a host that is ahead of it — by protocol or by version — without
--allow-downgrade; that host belongs to a newer rx.

Only the controller (where rx runs) needs external tools — ssh for every
operation, plus scp/curl/sha256sum for cache fetch/deploy. The remote needs nothing
preinstalled: rxd is a single static binary. Those tools are resolved through
PATH, so rx assumes a trusted PATH on the controller; it is a single-user
machine by design.

rx never prompts. Every ssh/scp invocation carries BatchMode=yes, so a host whose
credentials are not usable unattended fails immediately with `ssh_auth` and a
hint, instead of stalling on a password prompt or a GUI askpass dialog that no
agent harness can answer. Load keys into ssh-agent; check a host with
`ssh -o BatchMode=yes HOST true`.

Connecting is bounded at 10s (ConnectTimeout), so a black-holed host costs ten
seconds rather than the OS default of well over a minute — which matters because
rx has no fleet loop of its own: you iterate your inventory, and one dead host
must not stall it. Override with RX_CONNECT_TIMEOUT=<seconds> when a link is
genuinely slow to establish; it does not bound the command's own runtime (that is
--timeout on run/wait).

deploy uploads to a temp name and renames over ~/.local/bin/rxd, so a failed
transfer cannot leave a truncated binary and a currently-running rxd does not
block the install (an in-place write would fail with ETXTBSY).

Deploying ONE host that fails answers with a plain `error` object like any other
command — `deploy_failed` when the binary could not be obtained (no such release
asset, or nothing cached under --offline), or the usual `ssh_unreachable` /
`ssh_auth` when the transport is what broke. `deploy_failed` is not retryable:
its hint names the fixes that work (`--binary PATH` to push a local build,
`--offline` to use only the cache). Deploying SEVERAL hosts keeps the `deployed`
aggregate, since some may have succeeded, and each failed entry carries the same
code/retryable/hint — check `status` per host and exit 1 means at least one
failed.

`ping` is the preflight: one round trip tells you the host is reachable, what
rxd version/protocol it runs, and what it is (os/kernel/arch/distro) — enough to
choose a package manager or shell before a batch. It is a pure probe with no
side effects (it creates no state dir). It also reports `up_to_date` (does the
host's rxd match this rx exactly?) plus `local_version`, so version skew is
visible here rather than as a warning on every command — an older rxd is still
correct for most requests, so ping is where you check a fleet.

A missing or outdated remote is detected by probing rxd's `version` (its
protocol), not by guessing from stderr. Under --auto-deploy=local|on rx deploys
the matching rxd and retries; otherwise you get a typed `not_deployed` error
whose hint names the fix. rx never silently falls back to a plain SSH command.
Note: protocol equality is what makes a host "current", so a same-protocol rxd
update (a behavior fix that keeps the wire format) is not auto-detected — run
`rx deploy HOST` after upgrading rx to pick up rxd-side fixes. The exception is
`put -`, which additionally requires that the host not be *behind* this rx
before it will read stdin (a host that is ahead already has what it needs).

## Examples

  # preflight: reachable? which rxd? which OS/distro? (pick apk vs apt, sh vs bash)
  rx ping HOST

  # one call → exit code + output
  rx run HOST -- systemctl is-active nginx

  # feed stdin and get the result together
  printf 'c\na\nb\n' | rx run HOST -- sort

  # working directory + environment without a shell wrapper
  rx run HOST --cwd /srv/app --env NODE_ENV=production -- ./build.sh

  # elevate: passwordless doas, no TTY (do NOT use su — it needs /dev/tty)
  rx run HOST -- doas apt-get -y update
  printf 'key=value\n' | rx run HOST -- doas tee /etc/app.conf

  # start now, block for the result later (no polling)
  ID=$(rx start HOST -- ./migrate.sh | jq -r .id)
  rx wait HOST $ID --timeout 120

  # long-lived: take a handle now, read incrementally later
  ID=$(rx start HOST -- journalctl -fu nginx | jq -r .id)
  rx stdout HOST $ID --offset 0

  # interactive REPL over persistent stdin
  ID=$(rx start HOST -- python3 | jq -r .id)
  rx write HOST $ID "print(6*7)"
  rx stdout HOST $ID
  rx close-stdin HOST $ID

  # large or binary input streams unbounded via the pipe path
  cat firmware.bin | rx start HOST -- doas tee /var/lib/app/firmware.bin

  # write a file into place atomically, perms set before it becomes visible
  rx put ./app.conf HOST:/etc/app/app.conf --mode 0640

  # place a secret straight from a pipeline: no local temp file, no argv,
  # never world-readable, and an empty stream is refused rather than installed.
  # Any producer works — rxv, pass, op read, sops -d, a script.
  set -o pipefail
  rxv get host1/db_password | rx put - HOST:/run/secrets/db_pass --mode 0600

  # pull a file down atomically (size-verified); dump a live DB first
  rx run HOST -- doas -u postgres pg_dump -Fc appdb -f /tmp/appdb.dump
  rx get HOST:/tmp/appdb.dump ./appdb.dump
